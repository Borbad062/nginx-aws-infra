# Отчёт по проекту развёртывания инфраструктуры AWS с помощью Terraform и Ansible

## 1. Цель проекта

Цель проекта — автоматизировать создание облачной инфраструктуры в Amazon Web Services (AWS), развёртывание веб-серверов Nginx и проверку их работоспособности.

Для создания инфраструктуры используется Terraform, а для настройки операционной системы и веб-серверов — Ansible. Входящий HTTP-трафик распределяется между двумя веб-серверами с помощью Application Load Balancer (ALB).

В рамках проекта выполнены:
- создание виртуальной частной сети и подсетей;
- развёртывание трёх виртуальных машин EC2;
- настройка групп безопасности AWS;
- создание балансировщика нагрузки ALB;
- настройка DNS-записи через Route 53;
- установка и настройка Nginx с помощью Ansible;
- автоматическая проверка доступности веб-страницы каждые пять минут;
- проверка работоспособности приложения через доменное имя и адрес балансировщика.

## 2. Используемые технологии

## 3. Архитектура проекта

Инфраструктура размещена в регионе AWS `us-east-1`.

Основные параметры сети:
- VPC: `10.20.0.0/16`;
- первая подсеть: `10.20.1.0/24`;
- вторая подсеть: `10.20.2.0/24`.

В инфраструктуре используются три виртуальные машины EC2:
1. **Bastion Host** — сервер для административного доступа и выполнения команд Ansible.
2. **Web Server 1** — первый веб-сервер с установленным Nginx.
3. **Web Server 2** — второй веб-сервер с установленным Nginx.

ALB принимает HTTP-запросы и распределяет их между веб-серверами. DNS-имя `nginx.zubaidov.com` используется для обращения к веб-приложению.

Адрес балансировщика, полученный при проверке:

`nginx-aws-infra-alb-220218807.us-east-1.elb.amazonaws.com`

Схема взаимодействия компонентов:

```text
                 Пользователь
                      |
                      v
          nginx.zubaidov.com
                      |
                      v
          Application Load Balancer
                  /       \
                 v         v
          Web Server 1  Web Server 2
             Nginx         Nginx

          Bastion Host
                |
                v
              Ansible
                |
                v
       Настройка веб-серверов
```

Bastion Host предназначен для административного доступа. Конкретные ограничения сетевого доступа зависят от настроек Security Groups и UFW.

### 5.1. Каталог `terraform/`

В этом каталоге находятся конфигурационные файлы Terraform. Они описывают облачные ресурсы, которые необходимо создать в AWS.

**`main.tf` — основной файл конфигурации Terraform.**

Предназначен для объявления основных настроек проекта и подключения провайдера AWS. Здесь могут задаваться используемые провайдеры, их версии и общие параметры Terraform.

**`variables.tf` — входные переменные.**

Содержит объявления переменных, которые позволяют настраивать инфраструктуру без изменения основной конфигурации. В проекте используются параметры, связанные с адресом администратора, именем ключевой пары EC2 и включением DNS-записи.

Например:
- `admin_cidr` — диапазон IP-адресов, которым разрешён административный доступ;
- `key_name` — имя существующей ключевой пары AWS EC2;
- `enable_route53_record` — параметр включения или отключения создания DNS-записи.

**`vpc.tf` — конфигурация виртуальной сети.**

Предназначен для описания сетевой инфраструктуры:
- VPC с диапазоном `10.20.0.0/16`;
- подсетей `10.20.1.0/24` и `10.20.2.0/24`;
- связанных с ними сетевых компонентов, если они определены в конфигурации.

VPC обеспечивает логическое разделение инфраструктуры проекта от других сетей AWS.

**`ec2.tf` — создание виртуальных машин.**

Содержит определения ресурсов EC2. В рамках проекта создаются Bastion Host и два веб-сервера. В этом файле задаются параметры виртуальных машин, включая используемый образ ОС, тип экземпляра, сетевое размещение, ключевую пару и привязку групп безопасности.

**`security_groups.tf` — правила сетевого доступа AWS.**

Предназначен для описания групп безопасности и правил входящего и исходящего трафика. Такие правила определяют, какие подключения разрешены к виртуальным машинам и другим ресурсам.

Например, правила могут разрешать HTTP-трафик на порт 80 и административное подключение по SSH на порт 22 с ограниченного набора IP-адресов или от определённых групп безопасности.

**`alb.tf` — балансировщик нагрузки.**

Содержит конфигурацию Application Load Balancer и связанных ресурсов. В зависимости от реализации здесь описываются:
- сам ALB;
- целевая группа веб-серверов;
- обработчик HTTP-запросов на порту 80;
- регистрация веб-серверов в целевой группе;
- проверки состояния целевых серверов.

Балансировщик направляет входящие HTTP-запросы к доступным веб-серверам.

**`route53.tf` — DNS-настройки.**

Предназначен для настройки DNS-записи в AWS Route 53. Запись связывает доменное имя `nginx.zubaidov.com` с балансировщиком нагрузки.

В проекте предусмотрен параметр `enable_route53_record`, позволяющий управлять созданием DNS-записи.

**`outputs.tf` — выходные значения Terraform.**

Содержит выходные параметры, которые Terraform показывает после создания инфраструктуры. В зависимости от определённых выходов здесь могут отображаться:
- DNS-имя балансировщика нагрузки;
- публичные IP-адреса виртуальных машин;
- идентификаторы созданных ресурсов;
- другие параметры, необходимые для дальнейшей настройки и проверки проекта.

### 5.2. Каталог `ansible/`

Каталог предназначен для автоматизированной настройки серверов после создания инфраструктуры средствами Terraform.

**`ansible.cfg` — настройки Ansible.**

Содержит параметры работы Ansible. В частности, в нём могут задаваться путь к инвентарю, расположение ролей, настройки подключения по SSH и другие параметры выполнения команд и плейбуков.

**`playbook.yml` — основной сценарий настройки серверов.**

Описывает последовательность задач, выполняемых на целевых машинах. Согласно используемому в проекте сценарию, задачи включают:
- установку Nginx;
- установку утилит `curl` и `ufw`;
- копирование веб-страницы на сервер;
- установку скрипта проверки доступности Nginx;
- создание файла журнала проверки;
- включение и запуск службы Nginx;
- настройку правил UFW;
- добавление задания в cron для периодической проверки;
- выполнение проверки сразу после настройки.

Плейбук позволяет выполнять перечисленные действия повторяемо и централизованно, без необходимости вручную настраивать каждый веб-сервер.

**`inventory/hosts.yml` — инвентарь серверов.**

Содержит перечень управляемых Ansible узлов и их групп. В инвентаре могут быть указаны группы `bastion` и `webservers`, адреса серверов, пользователь подключения и параметры SSH.

Инвентарь определяет, к каким машинам Ansible должен подключаться при выполнении команд и плейбуков.

**`group_vars/all.yml` — общие переменные.**

Содержит переменные, применяемые ко всем узлам соответствующей группы инвентаря и её дочерним группам. В зависимости от конфигурации это могут быть часовой пояс, общие параметры SSH, пути к файлам и другие настройки.

Важно использовать точное имя `all.yml`: если файл назван `all.ym`, Ansible не распознает его как ожидаемый файл переменных группы `all`.

**`group_vars/bastion.yml` — переменные Bastion Host.**

Предназначен для хранения параметров, относящихся к административному серверу. Например, здесь могут находиться специфичные настройки подключения или выполнения задач на Bastion Host.

**`group_vars/webservers.yml` — переменные веб-серверов.**

Содержит параметры, используемые при настройке Web Server 1 и Web Server 2. В проекте такие переменные могут определять:
- `web_root` — каталог размещения веб-страницы;
- `status_log` — путь к журналу проверки работоспособности;
- другие параметры установки и настройки Nginx.

**`files/index.html` — главная веб-страница.**

Содержит HTML-код страницы, которую Nginx возвращает при обращении к веб-серверу. Ansible копирует этот файл в корневой каталог сайта, заданный переменной `web_root`.

Благодаря этому оба веб-сервера могут обслуживать одинаковую страницу.

**`files/check_nginx.sh` — скрипт проверки Nginx.**

Содержит Bash-команды для проверки доступности локальной веб-страницы. Скрипт отправляет HTTP-запрос с помощью `curl`, получает код ответа и записывает результат в журнал.

Если ответ имеет код `200`, записывается сообщение об успешной проверке. В остальных случаях фиксируется ошибка и соответствующий HTTP-код либо код `000`, если запрос не удался.

Скрипт используется как для немедленной проверки после настройки, так и для периодического запуска через cron.

**`.ssh/key.pem` — приватный SSH-ключ.**

Предназначен для аутентификации при подключении к серверам по SSH, если этот ключ соответствует ключевой паре, использованной при создании EC2.


## 6. Создание инфраструктуры с помощью Terraform

Перейти в каталог Terraform:

```bash
cd nginx-aws-infra/terraform
```

Если вы уже находитесь в корне репозитория, используйте команду:

```bash
cd terraform/
```

Установить необходимые провайдеры и подготовить рабочую директорию:

```bash
terraform init
```

Отформатировать конфигурационные файлы:

```bash
terraform fmt -recursive
```

Проверить синтаксис и корректность конфигурации:

```bash
terraform validate
```

Сформировать план создания ресурсов:

```bash
terraform plan \
  -var='admin_cidr=ВАШ_ПУБЛИЧНЫЙ_IP/32' \
  -var='key_name=ИМЯ_EC2_KEY_PAIR' \
  -var='enable_route53_record=true'
```

После проверки плана применить конфигурацию:

```bash
terraform apply \
  -var='admin_cidr=ВАШ_ПУБЛИЧНЫЙ_IP/32' \
  -var='key_name=ИМЯ_EC2_KEY_PAIR' \
  -var='enable_route53_record=true'
```

Значения `ВАШ_ПУБЛИЧНЫЙ_IP/32` и `ИМЯ_EC2_KEY_PAIR` необходимо заменить на реальные параметры. 

## 7. Настройка серверов с помощью Ansible

После создания инфраструктуры необходимо перейти в каталог Ansible.

Если текущий каталог — `nginx-aws-infra/terraform/`, выполнить:

```bash
cd ../ansible/
```

Если текущий каталог — корень репозитория, выполнить:

```bash
cd ansible/
```

Установка Ansible на Ubuntu, например на Bastion Host:

```bash
sudo apt update
sudo apt install -y ansible
ansible --version
```

Установка используемой коллекции Ansible:

```bash
ansible-galaxy collection install community.general
```

Проверка доступности целевых серверов:

```bash
ansible webservers -m ping
```

Запуск основного плейбука:

```bash
ansible-playbook -i inventory/hosts.yml playbook.yml
```

Для успешного выполнения необходимо, чтобы инвентарь содержал правильные адреса серверов, SSH-подключение было настроено, а у пользователя Ansible имелись необходимые права.

## 8. Проверка доступности Nginx

Для проверки локальной страницы используется скрипт `check_nginx.sh`.

Пример логики проверки:

```bash
#!/bin/bash

URL="http://127.0.0.1/"
LOG_FILE="/home/ubuntu/nginx_status.log"

HTTP_CODE="$(curl -sS -o /dev/null \
  --connect-timeout 5 --max-time 10 \
  -w '%{http_code}' "$URL" 2>/dev/null)" || HTTP_CODE="000"

TIMESTAMP="$(date '+%Y-%m-%d %H:%M:%S')"

if [ "$HTTP_CODE" = "200" ]; then
    echo "$TIMESTAMP - SUCCESS: Page is available (HTTP $HTTP_CODE)" >> "$LOG_FILE"
else
    echo "$TIMESTAMP - FAILURE: Page is NOT available (HTTP $HTTP_CODE)" >> "$LOG_FILE"
fi
```

В скрипте используется адрес `127.0.0.1`, чтобы обращаться к локальному IPv4-интерфейсу без неоднозначности разрешения имени `localhost`.

Код ответа `200` означает, что HTTP-запрос завершился успешно. Код `000` используется в данном скрипте как обозначение того, что получить HTTP-код не удалось, например из-за ошибки соединения или тайм-аута.

Для периодического запуска через cron используется интервал в пять минут.

Пример просмотра журнала:

```bash
cat /home/ubuntu/nginx_status.log
```

## 10. Различия между AWS Security Groups и UFW

В проекте используются два уровня сетевой фильтрации.

**AWS Security Groups** работают на уровне облачной инфраструктуры AWS и определяют разрешённый входящий и исходящий трафик для сетевых интерфейсов ресурсов.

**UFW** работает внутри операционной системы Ubuntu и управляет правилами локального межсетевого экрана.

Если подключение запрещено группой безопасности AWS, разрешающее правило UFW не позволит обойти этот запрет. Для успешного подключения трафик должен пройти все применимые уровни фильтрации.

При проверке UFW на веб-серверах были обнаружены правила:

```text
22/tcp ALLOW IN Anywhere
80/tcp ALLOW IN Anywhere
```

Это означает, что локальный межсетевой экран разрешал входящие подключения к SSH и HTTP со всех IPv4-адресов, а также были показаны соответствующие правила IPv6.

На момент проверки эти правила оставлены без изменения, поскольку основной контроль сетевого доступа предполагалось осуществлять через AWS Security Groups, а UFW рассматривался как дополнительный уровень защиты.

## 11. Ошибки, обнаруженные при использовании ИИ, и способы их исправления

| № | Ошибка или проблема | Как обнаружена и исправлена |
|---|---|---|
| 1 | В health-check-скрипте HTTP-код сравнивался через `-eq`. Это оператор для чисел, и если `curl` возвращал пустую строку, сравнение падало с ошибкой `integer expression expected`. | Проверено поведение при пустом значении. Сравнение заменено на строковое: `[ "$HTTP_CODE" = "200" ]`. |
| 2 | Имя `localhost` могло разрешаться в IPv4-адрес `127.0.0.1` или IPv6-адрес `::1`. Если Nginx слушал только IPv4, запрос через IPv6 мог завершаться неудачно. | Проверены `getent hosts localhost`, `curl localhost` и `curl 127.0.0.1`. В проблемном случае первый запрос возвращал код `000`, а второй — `200`. Для проверки использован `127.0.0.1`. |
| 3 | При ошибке `curl`, например при сбое подключения или тайм-ауте, HTTP-код мог оказаться пустым, что затрудняло диагностику. | Добавлена обработка ошибки: `|| HTTP_CODE="000"`. Теперь скрипт записывает в журнал понятный код отсутствия HTTP-ответа. |
| 4 | UFW на веб-серверах разрешал SSH и HTTP с любых адресов: `22/tcp ALLOW IN Anywhere` и `80/tcp ALLOW IN Anywhere`. | Проверено состояние через `ufw status verbose`. На момент проверки правила оставлены как есть; основной контроль доступа выполняют AWS Security Groups, а UFW является дополнительным слоем. Более строгие правила рекомендуется настроить отдельно. |
| 5 | Файл общих переменных был назван `all.ym` вместо `all.yml`, поэтому Ansible не загружал ожидаемые переменные, включая `timezone` и `ansible_private_key_file`. | Проверен вывод `ansible-inventory --list`. Файл переименован в `all.yml`, после чего переменные стали применяться. |

В рамках проекта реализован подход к автоматизированному развёртыванию веб-инфраструктуры в AWS с использованием Terraform и Ansible.

Terraform применяется для описания и создания сетевых ресурсов, виртуальных машин, групп безопасности, балансировщика нагрузки и DNS-настроек. Ansible используется для установки и настройки Nginx, размещения веб-страницы, настройки проверки доступности и организации журналирования.

Проверки через доменное имя и DNS-имя ALB возвращали `HTTP 200 OK`. В журнале также были зафиксированы успешные проверки локальной веб-страницы.

В ходе работы были выявлены и исправлены ошибки в Bash-скрипте и конфигурации Ansible. Дополнительно рассмотрены различия между облачными группами безопасности AWS и локальным межсетевым экраном UFW, а также способы ограничения административного доступа.

В результате получена инфраструктура, в которой создание облачных ресурсов и настройка веб-серверов выполняются средствами автоматизации, а доступность веб-страницы проверяется регулярно.
