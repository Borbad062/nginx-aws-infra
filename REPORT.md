# Отчёт по проекту: развёртывание веб-инфраструктуры в AWS с использованием Terraform и Ansible

## 1. Цель проекта

Цель проекта — развернуть веб-инфраструктуру в Amazon Web Services (AWS) с использованием Infrastructure as Code (IaC), автоматизировать настройку серверов и обеспечить проверку доступности веб-сайта.

В рамках проекта необходимо:
- Создать сетевую инфраструктуру AWS с помощью Terraform.
- Развернуть Bastion Host и два веб-сервера на EC2.
- Настроить балансировщик нагрузки Application Load Balancer (ALB).
- Установить и настроить Nginx с помощью Ansible.
- Настроить правила сетевого доступа.
- Реализовать автоматическую проверку доступности веб-сайта с помощью Bash и cron.

## 3. Архитектура инфраструктуры

Инфраструктура развёрнута в регионе AWS `us-east-1`.

Основные параметры сети:
- VPC: `10.20.0.0/16`.
- Подсеть 1: `10.20.1.0/24`.
- Подсеть 2: `10.20.2.0/24`.

В инфраструктуре предусмотрены три виртуальные машины EC2:

1. **Bastion Host** — сервер для административного доступа.
2. **Web Server 1** — первый веб-сервер с Nginx.
3. **Web Server 2** — второй веб-сервер с Nginx.

Внешние HTTP-запросы поступают на Application Load Balancer, который распределяет их между веб-серверами. DNS-имя используется для обращения к сайту.

**Домен проекта:** `http://nginx.zubaidov.com`

**DNS-имя балансировщика:**

`nginx-aws-infra-alb-220218807.us-east-1.elb.amazonaws.com`

## 5. Создание инфраструктуры с помощью Terraform

Terraform используется для автоматизированного создания сетевых ресурсов, виртуальных машин, правил сетевого доступа, балансировщика нагрузки и DNS-записей.

### 5.1. Переход в каталог Terraform

Из корневого каталога проекта выполнить:

```bash
cd terraform/
```

Если текущий терминал находится в другом каталоге, содержащем репозиторий, можно выполнить:

```bash
cd nginx-aws-infra/terraform/
```

Нужно использовать команду, соответствующую текущему расположению терминала.

### 5.2. Инициализация и проверка конфигурации

```bash
terraform init
terraform fmt -recursive
terraform validate
```

Назначение команд:

- `terraform init` — инициализирует проект и загружает необходимые провайдеры.
- `terraform fmt -recursive` — форматирует Terraform-конфигурации.
- `terraform validate` — проверяет корректность конфигурации.

### 5.3. Проверка плана развёртывания

```bash
terraform plan \
  -var='admin_cidr=ВАШ_ПУБЛИЧНЫЙ_IP/32' \
  -var='key_name=ИМЯ_EC2_KEY_PAIR' \
  -var='enable_route53_record=true'
```

Команда показывает, какие ресурсы Terraform планирует создать, изменить или удалить.

### 5.4. Создание инфраструктуры

```bash
terraform apply \
  -var='admin_cidr=ВАШ_ПУБЛИЧНЫЙ_IP/32' \
  -var='key_name=ИМЯ_EC2_KEY_PAIR' \
  -var='enable_route53_record=true'
```

Перед выполнением команды необходимо заменить `ВАШ_ПУБЛИЧНЫЙ_IP/32` на публичный IP-адрес администратора с маской `/32`, а `ИМЯ_EC2_KEY_PAIR` — на имя существующего EC2 Key Pair в AWS.

После проверки плана Terraform создаёт ресурсы в соответствии с конфигурацией проекта. При запросе подтверждения необходимо проверить план и подтвердить создание ресурсов.

## 6. Настройка серверов с помощью Ansible

Ansible используется для автоматизации установки и настройки Nginx, копирования файлов сайта, настройки UFW и создания задачи cron для проверки доступности веб-сервера.

### 6.1. Переход в каталог Ansible

После выполнения команд Terraform, если текущий каталог — `nginx-aws-infra/terraform/`, выполнить:

```bash
cd ../ansible/
```

Альтернативно, если терминал находится в корневом каталоге репозитория:

```bash
cd ansible/
```

### 6.2. Установка Ansible

Если Ansible ещё не установлен на Bastion Host:

```bash
sudo apt update
sudo apt install -y ansible
ansible --version
```

### 6.3. Установка коллекции для UFW

```bash
ansible-galaxy collection install community.general
```

Коллекция `community.general` предоставляет модуль для управления правилами UFW.

### 6.4. Проверка доступности серверов

```bash
ansible webservers -m ping
```

Команда проверяет возможность подключения Ansible к хостам, входящим в группу `webservers` в inventory.

### 6.5. Запуск playbook

```bash
ansible-playbook -i inventory/hosts.yml playbook.yml
```

Playbook выполняет следующие действия:

1. Обновляет кэш пакетов и устанавливает Nginx, curl и UFW.
2. Копирует файл `index.html` в каталог веб-сервера.
3. Устанавливает скрипт проверки в `/usr/local/bin/check_nginx.sh`.
4. Создаёт файл журнала состояния.
5. Включает и запускает Nginx.
6. Настраивает правила UFW.
7. Добавляет задачу cron для проверки сайта каждые пять минут.
8. Запускает проверку сразу после настройки.

Переменные `web_root` и `status_log` должны быть определены в Ansible variables.

## 7. Скрипт проверки доступности Nginx

Для проверки работоспособности веб-сервера используется Bash-скрипт `check_nginx.sh`.

```bash
#!/bin/bash

URL="http://127.0.0.1/"
LOG_FILE="/home/ubuntu/nginx_status.log"

HTTP_CODE="$(curl -sS -o /dev/null \
  --connect-timeout 5 --max-time 10 \
  -w '%{http_code}' "$URL" 2>/dev/null)" || HTTP_CODE="000"

TIMESTAMP="$(date '+%Y-%m-%d %H:%M:%S')"

if [ "$HTTP_CODE" = "200" ]; then
    echo "$TIMESTAMP - SUCCESS: Page is available (HTTP $HTTP_CODE)" >> "$LOG_FILE"
else
    echo "$TIMESTAMP - FAILURE: Page is NOT available (HTTP $HTTP_CODE)" >> "$LOG_FILE"
fi
```

Скрипт отправляет HTTP-запрос локальному Nginx и получает код ответа.

- Если код ответа равен `200`, в журнал записывается успешная проверка.
- Если получен другой код ответа, фиксируется неуспешная проверка.
- Если `curl` завершается ошибкой, переменной `HTTP_CODE` присваивается значение `000`.

Для обращения к локальному серверу используется `127.0.0.1`, чтобы явно указать IPv4 loopback и избежать проблем, связанных с разрешением имени `localhost` в IPv6-адрес `::1`.

Скрипт запускается через cron каждые пять минут. Результаты сохраняются в `/home/ubuntu/nginx_status.log`.

## 8. Security Groups и UFW

В проекте рассматривались два уровня фильтрации сетевого трафика: Security Groups AWS и UFW внутри Ubuntu.

| Параметр | Security Groups (SG) | UFW |
|---|---|---|
| Уровень работы | Сетевая инфраструктура AWS | Операционная система Ubuntu |
| Назначение | Ограничение доступа к ресурсам EC2 | Фильтрация трафика на самом сервере |
| Пример правила | Разрешить SSH только от Bastion Host | Разрешить входящий TCP-порт 22 |
| Роль в проекте | Основной механизм ограничения доступа в AWS | Дополнительный уровень защиты |

Например, UFW может содержать правило:

```text
22/tcp ALLOW IN Anywhere
```

Это означает, что UFW разрешает SSH-подключения с любых IP-адресов. Однако если Security Group веб-сервера разрешает SSH только от Bastion Host, прямое подключение с других источников будет заблокировано на уровне AWS.

**Таким образом, разрешение порта 22 в UFW не отменяет ограничений Security Group.** Входящий трафик должен пройти оба уровня фильтрации. UFW не может открыть соединение, запрещённое Security Group.

Для ограничения сетевого доступа в рамках проекта можно обойтись только Security Groups при условии, что они настроены корректно:

- SSH к веб-серверам разрешён только от Bastion Host.
- HTTP-трафик к веб-серверам разрешён от Application Load Balancer.
- SSH-доступ к Bastion Host разрешён только с доверенного IP-адреса администратора.

В такой конфигурации UFW является дополнительным уровнем защиты, а не обязательным условием работы инфраструктуры.

Для более строгой изоляции веб-серверы можно разместить в приватных подсетях без публичных IP-адресов, а Bastion Host использовать для административного доступа. Для исходящего доступа из приватных подсетей при необходимости можно использовать NAT Gateway.

## 10. Использование ИИ и исправление ошибок

ИИ использовался как вспомогательный инструмент при разработке Terraform-конфигураций, Ansible playbook и Bash-скрипта. Он помогал разбирать команды, предлагал варианты реализации и объяснял причины возникающих ошибок.

Однако предложенные решения проверялись на практике. В ходе самостоятельного анализа скриптов и конфигураций были обнаружены проблемы, после чего в код внесены исправления.

| № | Проблема | Как выявлена | Исправление |
|---:|---|---|---|
| 1 | В health-check-скрипте я сравнивал HTTP-код через `-eq`. Это оператор для чисел, и если `curl` возвращал пустую строку, сравнение падало с ошибкой `integer expression expected`. | Заметил при разборе скрипта: `-eq` требует, чтобы оба значения были целыми числами. Проверил на пустой строке — получил ошибку. | Заменил на строковое сравнение `= "200"`. Строки сравниваются безопасно, без приведения типов. |
| 2 | В скрипте стоял адрес `localhost`. Я не учёл, что это имя может резолвиться как в IPv4 (`127.0.0.1`), так и в IPv6 (`::1`). Если Nginx слушает только IPv4, запрос через `localhost` уходил в `::1` и получал отказ. | Выполнил `getent hosts localhost` — увидел и `::1`, и `127.0.0.1`. Сравнил `curl` к `localhost` и к `127.0.0.1`: первый давал `000`, второй — `200`. | Заменил `localhost` на `127.0.0.1` — это однозначный IPv4 loopback, не зависит от настроек резолвинга. |
| 3 | Если `curl` вообще не мог выполниться (нет соединения, таймаут), переменная `HTTP_CODE` оставалась пустой. В лог попадала строка без кода, и было непонятно, что именно произошло. | Проанализировал обработку ошибки: command substitution при сбое возвращает пустую строку, и условие `= "200"` просто даёт «ложь», но причина не фиксируется. | Добавил `\|\| HTTP_CODE="000"`. Теперь при любом сбое `curl` в лог пишется явный код `000` — видно, что проверка не удалась. |
| 4 | UFW на веб-серверах разрешал SSH и HTTP от Anywhere, то есть от любого источника. Формально это работает, но не соответствует идее ограниченного доступа. | Посмотрел вывод `ufw status verbose` — в правилах `22/tcp ALLOW IN Anywhere` и `80/tcp ALLOW IN Anywhere`. | Обсудил вариант с ограничением SSH по IP бастиона (`from_ip`). Пока оставил как есть: основной контроль доступа выполняют AWS Security Groups, UFW — второй слой. |
| 6 | Файл переменных назывался `all.ym` вместо `all.yml`. Ansible не подхватывал его — переменные `timezone` и `ansible_private_key_file` не применялись. | Запустил `ansible-inventory --list` и не увидел ожидаемых переменных из группы `all`. Проверил имена файлов в `group_vars/` — обнаружил опечатку в расширении. | Переименовал `all.ym` в `all.yml`. После этого переменные начали применяться. |

Таким образом, ИИ помог ускорить поиск решений и разобраться в причинах ошибок, однако его предложения не принимались без проверки. Исправления выполнялись на основе результатов команд, анализа конфигурационных файлов и фактического поведения инфраструктуры.

В ходе проекта была разработана инфраструктура AWS с использованием Terraform и автоматизирована настройка веб-серверов посредством Ansible. Для обработки HTTP-запросов использовался Nginx, а Application Load Balancer обеспечивал точку входа для обращений к веб-серверам.

Проект позволил получить практический опыт работы с Infrastructure as Code, автоматизации конфигурации серверов, организации сетевого доступа и базового мониторинга веб-сервиса. ИИ использовался как вспомогательный инструмент, а корректность итоговых решений проверялась самостоятельно.
